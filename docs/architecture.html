1. Product

Pansuthong is a local-first task tracker. Tasks and tags are the product center (no Projects). Views are computed queries over the in-memory document — they are never persisted as lists.

  • IDs: production net.puetsua.pansutong; testing target net.puetsua.pansutong.dev (Pansuthong Dev only).
  • Frontend: src/ — React 19, TypeScript, Vite.
  • Backend: src-tauri/ — Rust / Tauri 2 commands, SQLite store, sync.
  • Wire types: Rust model.rs ↔ TS src/lib/tauri.ts.
Model changes must stay backward-compatible (serde defaults, optional TS keys, schema version gate). Settings and data-folder choice are device-local and never written into the synced document.

2. Runtime layers

A mutation flows UI → IPC command → AppState write → SQLite Document (+ history append / attachment files). Peer changes reload the store and emit store-changed so the React tree refreshes.

3. Data folder layout

Synced data lives in a user-chosen (or default app-data) folder. Each device owns files named with its device_id. Peers’ replicas are read-only merge inputs.

sync-folder/ ├── tasks_<device>.db # this device’s Document (SQLite, rollback journal) ├── tasks_<peer>.db # peer replicas (merged read-only) ├── history_<device>.jsonl # append-only change log ├── history_<peer>.jsonl ├── attachments_<device>/ # managed blobs for this device │ └── attachment_* └── (legacy) tasks.json / tasks_*.json / flat attachment_*
  • SQLite uses rollback-journal mode so exactly one .db file exists at rest (no -wal/-shm for cloud clients to desync).
  • Entities are stored as serde-JSON in a data column; schema version is PRAGMA user_version.
  • Cross-device change detection hashes the decoded document content, not file bytes (identical content ≠ byte-identical DBs).
  • Legacy JSON is imported on first launch and left as a downgrade fallback.

4. Three consistency models

The sync folder holds three related kinds of data. They share device-id naming but do not share one merge/delete protocol — do not treat a single tasks_*.db as master for history or blobs.

Kind On disk Cross-device behavior
Document
tasks / tags / templates		 tasks_<device>.db Active merge: entity-level LWW + tombstones. UI uses the merged in-memory Document.
History history_<device>.jsonl Append-only per device; UI concatenates at read time. Peer merge does not append into the local sidecar.
Attachments attachments_<device>/ + metadata in Document Metadata unions by id (+ attachment tombstones in Document). Blobs sync as files; local GC when unreferenced.

Document merge (LWW + tombstones)

  • Each replica is a full Document; merge_documents in model.rs picks the latest entity stamp per id.
  • Deletes leave tombstones (deleted_tasks / deleted_tags / …) so stale replicas cannot resurrect entities.
  • Time entries and attachment metadata on the winning task are unioned by id.
  • Limitation: concurrent edits to the same entity silently drop the loser (no conflict file). External cloud clients may still leave *.sync-conflict* copies that the Conflicts UI surfaces.

5. Desktop folder sync vs Android SAF

User picks a sync folder (often a cloud-synced directory). sync.rs watches the parent with notify plus a 2s poll fallback (cloud clients often miss FS events on pull-down).

  • On change: content-hash compare → reload/merge peer tasks_*.db → emit store-changed.
  • Conflict copies from the cloud client are surfaced via conflict.rs / Conflicts view.
  • Attachments served to the webview via asset protocol scopes (flat legacy + per-device subdirs).

App-private tasks_<device>.db remains the crash-safe master. safsync.rs mirrors it (and attachments / conflict copies) to a user-picked SAF folder. Wire format matches desktop: per-device .db, legacy JSON peers still readable.

  • Frontend triggers: pull on launch + foreground; debounced push after local writes (store.ts).
  • On change: content-hash compare → merge peer replicas into the app-private master (same LWW as desktop) → emit store-changed.
  • Commands: saf_pick_folder, saf_push, saf_sync_now, saf_status, saf_clear_folder.
  • SafBackend trait keeps mirror logic testable off-device. External cloud conflict copies are still mirrored for the Conflicts UI.

6. Device-local config vs synced data

Device-local (not synced)

config.json in the default app-data dir (config.rs).

  • Chosen data-folder path / SAF folder handle
  • Theme, sort order, language, day-start hour
  • Upcoming horizon, reminder interval, sound, attachment size cap
  • Window geometry (desktop plugin state file)

A device-specific folder path never leaks into the synced Document.

Synced (per-device replicas)

Document: tags, tasks, template_tasks, tombstones, attachment metadata.

  • Tasks reference tags via tag_ids; tags are flat with priority weights
  • Task priority = max resolvable tag weight
  • completed_at is source of truth for done / archived
  • Templates live in template_tasks, not tasks
New Settings sections/controls need explicit product approval. Do not move settings back into the synced document.

7. Frontend map

Shells adapt layout (DesktopShell / MobileShell). useDocument() loads the document once, rebuilds indexes on every change, and on Android drives SAF pull/push.
